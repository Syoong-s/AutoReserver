# AutoReserve · 现代原生预约客户端

## 快速启动

在本仓库的 **Releases** 页面下载对应系统的便携包：

| 系统 | 下载的 Release 包 | 启动方式 |
| --- | --- | --- |
| Linux x86_64（Ubuntu 22.04+ 图形桌面） | `AutoReserve-0.12.0-linux-x86_64-portable.tar.gz` 或 `.zip` | 将整个文件夹解压到可写位置，双击其中的 `AutoReserve`。 |
| Windows 11 x64 | `AutoReserve-0.12.0-windows-x86_64-portable.zip` | 将整个文件夹解压到 Windows 本地可写磁盘，双击其中的 `AutoReserve.exe`；无需预装 Python 或 WSL。 |

请保留启动文件与解压后的其他文件，首次启动需联网下载缺少的依赖；配置保存在程序文件夹内的 `config/` 中。

Windows 用户下载 `windows-x86_64-portable.zip`，完整解压到 Windows 本地可写文件夹，双击其中的 **AutoReserve.exe**。无需安装 Python 或 WSL；包内附带私有 Python 和 GTK，首次启动将 Chromium 安装到程序文件夹。不要在压缩包内或 WSL 网络共享路径启动。配置仍位于该文件夹的 `config/`，具体步骤见 [Windows 说明](docs/WINDOWS.md)。

## 启动与登录

先关闭旧客户端，再在项目目录运行 `./start-gui.sh`。`./run.sh`、`./run.sh desktop`、`./run.sh gui` 也都会打开原生窗口。

点击侧栏 **登录 / 重新登录**，在网站主界面选择校内或校外登录，完成后回客户端点击 **保存登录**，不必进入具体场馆。主动登录使用全新临时浏览器，不载入过期 Cookie、localStorage、IndexedDB 或 sessionStorage，避免出现“显示已登录但个人信息为空”。服务器确认身份后才保存新会话；取消或失败不会覆盖原登录文件。正常监测仍复用已保存会话。

第一次没有 `.auth/catalog.json` 时，保存登录后会读取并缓存场馆、项目目录；请求按至少 2 秒串行间隔进行，不读取日期和空位。缓存存在后一直复用，启动和选择场馆都不自动刷新。损坏缓存会明确报错，不会静默访问网站重建。

## 窗口、滚动与固定监测区

主窗口使用 GTK 原生客户端标题栏（CSD），在首次映射前完成配置，不再通过 Tk/X11 属性反复隐藏系统边框。顶部可拖动和双击最大化，窗口边缘通过 GTK 原生方式缩放。设置、成功通知和退出确认均使用**仅关闭按钮**的原生子窗口，设置窗口不提供最小化或最大化按钮。

左侧目标使用 GtkListBox，放在独立 GtkScrolledWindow 中。滚动位置由 GtkAdjustment 维护，到顶后固定为零；状态更新复用现有行，不重建列表或反向计算滚动位置。每行 **+** 复制下一天，**×** 删除可编辑目标；底部保留排序与执行设置，不再提供活动区开关。

右侧工作台下方始终显示两个独立框：**执行记录**和**空位监测**。两框分别滚动，固定在编辑区外，滚动目标编辑内容不会隐藏它们。记录最多保留最近 250 条，查看历史记录时保持阅读位置；空位仅显示最近一次监测得到的快照，不提供隐式实时查询。小窗口可滚动编辑卡片继续访问下方场馆和时段。

场地和时段使用原生 GtkToggleButton / GtkFlowBox，周围留白与具体卡片都属于同一个原生滚动容器；无需把鼠标精准放到时段文字上才能滚动。选中态以蓝色边框、背景和文字区分，任意场地与具体场地点击互斥，支持原生 Tab、空格和回车操作。场馆草稿按目标独立保留并自动换行。

GTK 默认使用当前桌面的 Wayland 或 X11 后端。启动器会预检 GTK 动态库与浏览器依赖，缺少时按需在程序目录初始化，失败时给出诊断。终端打印“客户端窗口已创建并映射”表示 GTK 已建立窗口；若桌面会话本身异常，应先检查 WSLg。原 Tk 界面和诊断代码仅保留历史回归用途，默认入口、`gui` 别名和 `desktop` 均进入 GTK。

## 抢购模式与折叠工作台

右侧从上到下分为 **重复功能设置 → 抢购功能设置 → 目标设定** 三个原生折叠模块，各自独立展开/收起，按当前目标保留折叠状态。右上角始终显示 **抢购模式** 滑块；普通目标和重复模板均可独立开启，不影响其他目标。

1. 先按原方式添加目标、场馆、场地和时段。在右上开启抢购模式，抢购设置自动展开。
2. 普通目标填写完整抢购日期与时刻（北京时间，可到秒），与预约场地使用的日期分别设置。例如 10 月 28 日中午开抢 10 月 30 日的场地。重复模板填写执行日的 `HH:MM:SS`，沿用已选星期和预约日期偏移。
3. 默认提前 **45 秒**复查登录、估算网站时间并进入最高优先级场馆/日期。开抢前不会选场地或提交，准备阶段的空位快照不会用于下单。日期尚未开放时，在开抢后重载日历。
4. 默认最初 1 秒以 **250ms** 为目标间隔串行读取，账号内所有目标共同限制为首秒及滚动一秒内最多 **4 次读取动作**；随后 **8 秒**使用 **1000ms** 间隔，再恢复普通监测。网页自身的网络请求和稳定校验可能降低实际频率。
5. 保存后在准备时间到达前点击 **开始监测**，保持程序在线。滑块只改变设置，不会自行启动预约。模块内显示阶段、倒计时及校时质量。复制下一天也会顺延抢购日期，转换重复模板则保留每天的时刻。

网站 HTTP Date 只精确到秒，因此自动校时是偏差估算，界面明确显示约 ±500ms 加半程网络延迟的采样不确定性，无法承诺毫秒级准确。可以关闭自动校时或填写手动偏差补偿（正值表示服务器时间更快）。429/503 和 Retry-After、403 暂停、验证码、去重和提交后人工付款流程继续生效。详细配置、算法与网上脚本参考见 [抢购模式说明](docs/RUSH.md)。

## 一个目标可以选择多个场馆

1. 点击侧栏 **新建预约目标**，填写名称和日期。
2. 在下拉框选择场馆和项目，例如“学生中心 → 健身房”，选择具体场地，然后点 **加入场馆**。
3. 再选择其他场馆/项目，例如“体育馆 → 羽毛球”，继续点 **加入场馆**。已加入场馆显示为蓝色卡片，包含项目和具体场地；卡片自动换行，不再横向溢出。
4. 选择一个或多个时段，点击 **添加到当前目标**，一次生成所有已选场馆的候选。也可以每次选一个场馆后直接添加，逐步补充其他场馆。
5. 用候选列表上下箭头调整优先级。场馆、项目、具体场地和时段都属于这个候选；不同场馆可以设置不同的具体场地。
6. 其他日期建立其他目标。保存后点击 **开始监测**。

**同一目标的场馆是备选关系，任意一个成功下单就完成该目标，不会在其他备选场馆继续下单。多个独立目标则分别需要完成。** 全部目标和场馆共同监测，一个场馆无空位不会阻塞其他场馆或目标。

没有已知具体场地名时，选择 **任意可用场地**，监测启动后才从真实网格列名匹配。已经监测过的项目会单独缓存场地名称，供以后选择；不要把“健身房”等项目名称当成具体场地名。切换添加器中的场馆不会替换或隐藏目标。切换左侧目标会保留各自尚未添加的场馆选择；同一场馆/项目再次加入时更新该卡片的场地。

多个时段默认分别生成备选。勾选 **连续时段合并下单** 时，所选时段必须连续且全部可用，才作为一个订单。候选按显示顺序匹配；多个场馆都有空位时优先选择排名更高的候选。

## 下一天复制与按周重复

点击某目标右侧 **+**，会把该目标自身日期往后一天，完整复制场馆、项目、场地、时段和优先级。例如 10 月 30 日的目标会复制为 10 月 31 日，不以今天为基准。新目标使用独立 ID，不继承完成状态或重复设置；已完成目标也可复制。重复目标的 **+** 使用工作台显示的预计预约日期作为基准。创建后点击 **保存设置**。

在右侧顶部点击 **设为重复目标**，将当前普通目标转换为独立重复模板，左侧可直接选择编辑；原普通目标不会作为额外的一次性预约保留。至少添加一个场馆备选后才可转换。启用的重复目标在右侧以蓝色边框高亮，暂停后恢复普通边框。

每个重复目标分别配置：

- **自动预约日**：周一到周日任意组合，至少选一天；全选即每天重复。
- **执行时间**：北京时间 HH:MM，例如 12:00。
- **预约往后几天**：0–7，2 表示执行日的后天。
- **开启重复预约**：单独暂停或恢复该目标的后续生成。

星期按**自动执行当天**判断。例如选择周一、三、五，12:00、往后 2 天，会在这些执行日生成对应周三、五、日的预约。生成后尚未完成的日期目标继续参与共享监测；取消某个执行日或暂停模板只影响后续生成，已经生成的目标保留。各模板的候选和时间独立管理，模板编辑不会改写已生成的日期目标或订单。点击 **切换为普通目标** 可把当前模板转换为预计日期的一次性目标；已有日期实例仍保留。

旧规则自动以七天全选打开，可逐条改成所需星期，无需重新创建。规则只在 **保存设置** 并 **开始监测** 后执行；编辑与保存不查询空位。当前目标全部完成后，程序等待下一次选中的执行日，不会退出；没有待监测目标时不读取空位。重复模式优先于普通的完成后停止和限时监测设置。

同一规则同一天只生成一次；重启根据稳定 ID 和订单记录恢复，避免重复下单。晚于当天时间启动时仅在当天属于所选星期的情况下补建当天目标，不补历史。过去的安全日期实例会从列表整理移除，订单和占用时段记录继续保留，未知或待验证记录不会自动清理。

**客户端、WSL 和电脑需保持运行及联网。** 停止或关闭会暂停运行，重开后须再次点击开始。

## 下单成功弹窗

每个目标收到服务器成功响应和有效订单号后，立即显示原生成功提示窗，包含目标、场馆、项目、场地、日期、时段及订单号。

弹窗不阻塞监测，其他未完成目标继续运行；短时间多个目标完成会汇总到同一通知窗口。关闭弹窗不会停止任务。重复状态更新及重开程序不会重复弹出旧订单。拒绝、断网、验证码、缺少订单号等不确定结果不会被误报为成功。

程序不付款；弹窗表示订单已经提交，不代表网站完成了支付或权益确认。

## 监测频率与定时

侧栏 **执行设置** 可调整启动时间、全局读取间隔、随机延迟、退避、金额上限、全部完成后停止，以及是否显示预约浏览器。

- 默认全局间隔 15 秒，额外增加 0–20% 随机延迟。跨场馆切换、日期刷新和必要重载全部共用一个预算，不为每个场馆另开高频循环。
- 同一场馆/项目/日期的多个目标共用一次空位快照。先检查本轮各场馆，再按候选优先级匹配；下单前重新核对实际场馆、项目、日期、场地、时段、摘要及金额。
- 暂时加载超时进入共享指数退避，首次至少 30 秒；429/503 遵守 Retry-After，403 暂停全部监测。等待页面稳定仅检查本地 DOM。
- 只有启动监测后才读取空位。定时任务到达设定时间后才加载网格；使用北京时间，例如 `2026-10-28T12:00:00`，留空立即。
- 已点击提交但结果未知时，不会换另一个场馆再试。请先核对网站订单，持久锁会防止重复下单。

执行记录和最近空位在右侧工作台下方固定显示。GTK 主线程每 33ms 消费一次有时间预算的事件批次，合并进度更新并保留全部完成通知；不在每次检查中访问配置文件或订单数据库。场馆、时段选择只操作内存。浏览器操作、配置保存和保存后的本地状态读取都在后台执行。

## 首次启动与鼠标启动

发布便携包解压到可写文件夹后，直接双击其中的 **AutoReserve** 原生 Linux 启动文件；之后也可以从当前用户的应用菜单启动。源码目录可用 `./start-gui.sh`，或者先用 `python3 tools/release.py` 生成原生入口（构建机器需要 C 编译器，发布包用户无需编译）。

第一次启动自动检查依赖：Python 包装入 `.venv/`，Chromium/无头浏览器、缓存、下载工具和必要的 Linux 运行库/中文字体放入 `.runtime/`。Ubuntu 缺少的系统库只下载并解压到程序目录，不使用 sudo、不运行系统包安装，不修改全局 Python。适用自动安装环境是有图形会话和系统 Python 3 的 Ubuntu 22.04+ / WSLg。

成功验证实际浏览器并保存配置后，`config/config.json` 的 `initialized` 才设为 `true`；具体依赖记录在 `config/bootstrap.json`。后续启动仍会快速检查，缺文件或版本变化就修复，失败保持未完成状态，重新启动即可重试。缺依赖时需要网络；初始化不启动监测或真实预约。

应用菜单只添加当前用户的快捷方式，所有依赖保留在程序文件夹。移动目录后先在新位置双击一次以更新快捷方式和解释器路径。安装清单和限制见 [首次启动说明](docs/FIRST_RUN.md)。

## 配置位置与目标状态

默认配置固定保存到**程序目录内的 `config/config.json`**，从其他目录启动也不会变。首次启动会验证旧的根目录 `config.json`，再迁移到新位置；原文件保留为 `config/legacy-config.json`。已有新配置优先，私有登录和订单数据库仍在程序目录 `.auth/`，避免影响订单去重。显式 `--config` / `--auth-dir` 可用于独立测试。

左栏使用整行底色与左侧色条区分目标：运行中绿色、每周重复蓝色、未启动灰色、已完成紫色、需处理橙色。选中状态仍保留各类底色；重复目标在右侧同时显示蓝色边框。侧栏保留行、标题及状态缓存，未变化时不重新创建控件或写入文本。

本仓库不含账号、订单与个人配置，提供英文 README、MIT 协议、Git 忽略规则、Python 包、便携归档构建器与 GitHub 自动发布工作流。无需依赖原项目目录或 TeleMail；发布说明见 `docs/RELEASING.md`。

## 老目标与进度迁移

第一次打开 v0.5 时，会把当前配置与旧 `.auth/plans/` 中分场馆保存的目标合并成统一工作台，补齐每个候选的场馆信息。旧配置先备份到 `.auth/workspace-v1.json`，原项目文件保留。

目标来源信息保留旧订单身份，不受候选排序或添加器场馆选择影响。旧提交记录补充等价预约链接的场地去重索引，避免同一场馆不同入口再次提交相同时段。迁移完成后不会在每次启动重新合并。已有订单记录的目标只能调整排序或创建新目标，不能改成另一项预约要求。

登录有效期由网站决定；失效后重新登录保存即可，目录、目标和订单记录保留。程序需保持网络、WSL 和电脑在线。关闭正在工作的客户端会先请求停止；已提交则等待本次结果后关闭。

## 文件与运行环境

- `autoreserve/gtk_desktop.py`：GTK 工作台、固定记录/空位区域、设置与通知、主线程事件分发。
- `autoreserve/gtk_native.py`：有限的 GTK / GLib C ABI 绑定，显式类型签名与回调生命周期管理；不依赖 PyGObject/GIR。
- `autoreserve/gtk_ui/main.ui`、`style.css`：GtkBuilder 布局和 GTK CSS；不使用 HTML 或浏览器 WebView。
- `autoreserve/workspace.py`：与工具包无关的编辑状态、复制、每周规则与场馆草稿。
- `autoreserve/desktop_controller.py`：静态目录、跨场馆后台操作、迁移、保存与订单通知。
- `autoreserve/repeat.py`、`multivenue.py`、`runner.py`、`sjtu.py`：周调度、共享监测预算和持久下单保护。
- `autoreserve/desktop.py`：保留 CLI 启动兼容入口，转交 GTK；其中旧 Tk 类及配套模块仅用于历史回归。
- `.auth/`：私有登录、目录、场地名、迁移备份和订单记录，不要分享。
- `artifacts/gtk-rebuild/`：本次代码备份、截图、日志与差异。

通用 Linux / WSLg 环境需要 Python 3.12+、GTK 3.24+ 及其标准运行库、图形桌面会话与 `requirements.txt` 中的浏览器依赖。使用 Python 标准库 ctypes 调用原生 API，无需编译步骤。便携启动：`./start-gui.sh`；命令行配置检查：`./run.sh check`。

## 验证

运行 `./test.sh`。测试覆盖 GTK 真实窗口的首帧设置标题栏、仅关闭按钮、原生滚动上限、时段留白滚轮事件、固定双监测区、场馆草稿、目标复制、每周配置、后台保存、通知与协作关闭；另保留跨场馆调度、限流、持久去重、旧配置和历史界面回归。全部自动测试仅使用本地模拟站和私有临时文件，不占用真实名额。

语法检查：`python3 -m compileall -q autoreserve scripts tests demo`、`node --check autoreserve/ui/app.js`、`bash -n run.sh start-gui.sh test.sh`。源文件均使用 LF。

设计和验证见 [架构设计](docs/ARCHITECTURE.md)、[验证记录](docs/VALIDATION.md)。旧 `gui.py`/`ui/` 和 Tk 界面仅保留兼容回归代码，正常入口全部使用 GTK。
